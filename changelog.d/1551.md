### Fixed

- **A migration that cannot take its lock no longer queues every statement on the table behind it (#1515).** The runner applies each wrapped file in one transaction and set no `lock_timeout`. An `ALTER TABLE` waiting for ACCESS EXCLUSIVE behind any open transaction held its place in the lock queue, and every later statement on the table, readers included, waited behind it for as long as the holder ran. The runner now bounds each wrapped file's lock waits at 1 s (`LOCK_TIMEOUT`, set transaction-locally), under the app's own 2 s tap bound, so a statement queued behind a waiting migration does not fail on its own. Such a file fails with SQLSTATE 55P03 and leaves no ledger row and no partial change. The runner tries that failure again, and no other, after 1, 2, 4 and 8 s (`LOCK_RETRY_DELAYS_S`, about 20 s in all), and says so on stderr, so a transient holder costs seconds and not a deploy. A file that runs out of attempts fails the apply as any failure does, and the deploy aborts with the old version serving. Self-managed and no-transaction files run without the bound.
