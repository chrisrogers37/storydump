### Tests

- **The schedule verbs' gate runs the write verbs as the tables' owner too, where only their own SQL can refuse another workspace's ids (a follow-up to #1517).** `TestAnotherWorkspacesIdsAsTheTablesOwner` connects as `svc_migration`, which owns the tables, so row-level security does not filter it, and is not a superuser. A person of one workspace runs `schedule_item` with another workspace's account, its item, or both, and `reschedule_item` and `cancel` on its planned and its cadence story: seven cases. The session first reads those rows, which shows the policies are out of the way, and each command is still refused `not_found`, `schedule_item` naming what is `missing`. As `svc_ingress` the policies hide those rows whatever the SQL says, so a `workspace_id` predicate dropped from `schedule_item`'s reads or from `_intent_row` went unseen at the gate; `tests/mutations/content_schedule_05.sh` now runs those three mutants against this arm. `in_tenant` (`tests/scripts/conftest.py`) takes the user it asserts as `expect_user`, `svc_ingress` by default, as `txn` does.

- **Unit tests pin the plan horizon, every state a story cannot move from, and the serve sweep's due-time order (a follow-up to #1517).** `vocabulary.PLAN_HORIZON_DAYS` is 365; `reschedule_item` refuses a story in any state but `scheduled` as `illegal_transition`, the states read from `vocabulary.INTENT_STATES`; the serve sweep takes a story due earlier before one with a lower id. Each is written against a mutant the unit suite let through: a horizon of 364 or 366 days, a move from `approved` or `publishing`, and a sweep order that ignores the due time.
