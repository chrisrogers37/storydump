### Fixed

- **One reconciler row that fails no longer stops every other workspace's reconciliation (#1492).** `reconcile_ambiguous` ran every due row in one transaction. So a row that raised (a verdict whose flip matched no row, #1438's alarm) rolled back the verdicts before it, and, still due and still oldest, led the next 60-second beat into the same raise. Every workspace's unresolved publish stayed behind it, and through `uq_publish_exclusive` so did its account's next publish. The executor now owns its transactions: it reads the sweep in one short transaction and commits each row in one of its own, so a failed row rolls back alone and the rows behind it land. The alarm is unchanged: after the beat the first failure is re-raised, and the job fails and retries. A notice that reached nobody is recorded as attempted only by a beat that returns, never by its own row, so a failing beat cannot leave the owed notice reading as told for the rest of its window. A transaction per row carries no savepoint from one row to the next, so the batch can never outgrow the 64 writing subtransactions a backend caches (#1441), whatever `reconcile_limit` is set to.
