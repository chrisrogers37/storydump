### Fixed

- **A worker handover gives the clock to the new worker at once.** The clock took its election lock again on every tick, and PostgreSQL counts each one, so the single release at a clean shutdown left the lock held until the old worker's database session ended; through a connection pooler that session could outlive the worker, and no new worker became the clock. The clock now takes the lock only when its own session does not hold it already, read from `pg_locks` on each tick, so it holds one count and its release frees it.
- **The worker and the migration runner refuse a pooled database host.** Both hold a session-scoped advisory lock, which a transaction pooler such as Neon's `-pooler` endpoint can keep on a pooled server session after the process lets go. The worker exits 2 at boot when `TARGET_DATABASE_URL` names a host whose first label ends in `-pooler`, names no host (the driver would take one from the environment), or cannot be read. The runner refuses to run where libpq connected to such a host, before it takes its lock, whatever form its connection string takes. The deploy then fails while the previous version keeps serving. Use the endpoint's direct host.
- **A deploy's migration step no longer waits forever for the runner lock.** It waits at most five minutes for another run, naming the session that holds the lock before and after the wait, and then fails the deploy. It waits by trying the lock every half second with no transaction open, so the other run's `CREATE INDEX CONCURRENTLY`, which waits for every older snapshot, can no longer deadlock with it and leave an invalid index. It also gives the lock back before it closes its connection, and says so when its session no longer held it.
- **A migration file that leaves its own transaction open fails the run.** A self-managed file with a `BEGIN` and no `COMMIT` printed as applied and exited 0: applied last, its work and its ledger row were rolled back when the runner gave its lock back; followed by a wrapped file, that file's `COMMIT` committed both. The run now fails at that file, naming it and its mode (self-managed or no-transaction), before its ledger row and before any later file runs: "migration <file>: a self-managed file left its transaction open; the open transaction was rolled back and the file is not recorded". Whatever the file committed before that `BEGIN` stays committed.
- **The migration runner's `apply`, `adopt`, `convert-ledger`, `repair` and `status` no longer print the password of a database URL they cannot read.** libpq's refusal of a malformed connection string, such as an unencoded `%` in the password, a misspelt query parameter or an unknown key/value option, quoted the text it could not parse in a traceback. These verbs now exit 1 with "the runner's database URL is not one libpq can read; percent-encode @ / ? # % in the user or password, and check each query parameter's (or key/value option's) name and its =", and carry none of libpq's error with them. `parity` connects through `scripts/schema_parity.py` and still reports such a URL as before.
