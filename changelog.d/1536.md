### Added

- **The owner can read the activation funnel across every workspace, in counts: how many people who signed up went on to create a workspace, connect Instagram, add a folder and approve a first story, and how many stalled at each step (migration 104, `07` §47; #1481).** `fn_activation_funnel(p_since, p_stall)` returns five rows, one per stage (`o_ordinal`, `o_stage`, `o_reached`, `o_stalled`), for the active users created since `p_since`, following the active workspaces they own. Each stage is the earliest record the product already writes: the sign-up, the first owned workspace, the first `ig_accounts` and `media_sources` rows in one, and the first audit row the trigger wrote moving a story from `awaiting_approval` to `approved` or `posted`, so a manual "Posted myself" counts as the first approval. A person is stalled when a stage is missing and nothing has happened for `p_stall` (72 hours unless the caller passes another window). They count against the stage before the missing one, and someone who joined another person's workspace is never counted as stalled. No id, name or email leaves the door. **This is a security-model change.** The door is SECURITY DEFINER and owned by `svc_maintenance`, which gains a `SELECT` grant and a `USING (true)` read policy on `users` (`p_maint_users`) and `workspace_members` (`p_maint_members`); it already read `workspaces`, `ig_accounts`, `media_sources` and `audit_events`. `EXECUTE` goes to `svc_worker` alone, the login the owner's `psql` escape hatch connects as, and never to `svc_ingress`, so no API route or CLI verb can serve the counts until an operator principal exists (#1124). `documentation/operations/reading-the-ledger.md` carries the one query. `tests/scripts/test_activation_funnel_gate.py` pins the stage counts, the stall window, the result's columns and the grant on a real PostgreSQL, and the RLS runtime harness registers the door and its two policies. A schema change, awaiting the owner's approval.
