### Added

- **A worker whose event loop stops turning now ends itself, so the platform restarts it (#1664).** The worker was fail-fast for a task that dies, but everything that noticed ran on the event loop, so a loop that stopped (a call that does not return on its thread, or a process stopped and resumed) left a live process that did nothing and logged nothing. A watchdog thread (`src/services/target/loop_watchdog.py`), armed for the whole of the worker's run, now ends the process with exit 3 when the loop has been silent for 300 s (`loop_stall_seconds`), or when the thread itself was absent for longer than that and one beat between two checks, after writing every thread's stack to stderr: the stuck thread's frame names the call. It never acts on a loop that turns while its tasks wait on a database or a provider, because from inside a wait that will never end looks the same as an outage, and exiting through an outage spends the restart budget. The status line gains `watchdog[armed]`. It cannot help when the process no longer runs at all, which is what the monitor's page is for, nor see a call that holds the interpreter lock until that call returns.
