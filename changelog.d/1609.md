### Changed

- **The invitations listing reads its floor from the command table, so it cannot drift from minting's (#1609).** The pending-invitations listing gated with `admin_session`'s literal admin floor, and only a docstring said that was the floor `invite_member` mints at. It now gates at `commands.ROLE_FLOOR["invite_member"]` through the new `principal.floor_session`, which takes the floor as an argument; `member_session` and `admin_session` are that gate at a fixed floor. A test moves the minting floor and requires the listing's gate to follow. Behaviour is unchanged: both floors are admin today.
- **The session gates set the tenant once per gated request, not twice (#1607).** `floor_session`'s unit of work already binds the claimed workspace as the tenant, so its `authorize_member` call passes `tenant_bound=True` and skips the repeated `set_config`: one database round trip fewer on every member- and admin-gated request. The membership read still binds both the workspace and the user. A test runs each allowed and refused case through the gate that binds the claim itself and through the session gate, and requires the same decision.
