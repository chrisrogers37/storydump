### Fixed

- **Behind Railway's edge, every visitor counted as one address to the rate limits.** Production's access log showed each request arriving from Railway's edge in `100.64.0.0/10`, which `TRUSTED_PROXY_HOSTS` did not include, so the API ignored `X-Forwarded-For` and keyed sign-in's pre-auth counter (30 a minute) on the edge's address: one visitor's burst refused everyone. The waitlist was unaffected in production, where the site names each visitor (`WAITLIST_SITE_SECRET`). The default now trusts `100.64.0.0/10` too, and the right-to-left walk lands on the address Railway's edge observed, so a forged entry left of it still never wins. When Railway routes a request through its Fastly CDN the header arrives as `<client>, <Fastly edge>`, and the walk stops at the Fastly address on purpose: skipping it would let anyone who fronts the API with their own Fastly service write the client entry. Sign-in's counter now keys an IPv6 visitor on their /64, as the waitlist already did (`principal.address_key`), so walking one subscriber's addresses is not a fresh limit per request.
