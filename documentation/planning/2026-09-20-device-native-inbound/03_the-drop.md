## Summary

The dispatcher recognises a photo or video from a linked, active member in a bound group and enqueues one job, inside a savepoint in the delivery's own transaction, so nothing it does can fail or redeliver the delivery. The job runs on the interactive lane, serialized per workspace, and owns its transactions: it checks the workspace's "Telegram drops" folder under the current Drive grant or creates one (admitting a new drop source to the mix), downloads the file from Telegram, uploads it into the folder, records the item at once and mints a demand sync as a backstop, and reacts to the message. A refusal is one reply, paced and threaded to the message, written with the job's own finalize so it is sent exactly once; a drop that runs out of retries is told so. Nothing is accepted that the story path cannot carry, and GIFs, stickers and video notes are not drops. Two PRs: **03a** adds the Telegram transport methods and the Drive write leg, pure additions with their tests; **03b** adds the migration, the recognition, the admission, the executor, the surfaces and the docs. Which messages count, whether an admin switch gates them, and who may drop are F11's; the text marks each place the ruling lands.

### Steps

**PR 03a — the transport and the Drive write leg (pure additions).**

1. **The transport.** `telegram_transport.py`: `get_file(file_id) -> dict` (`getFile`); `download_file(file_path, *, max_bytes) -> bytes` — GET `{_api_base}/file/bot{token}/{file_path}` through `egress.request` under `timeout_class="upload"`, `total_budget_s` at the media-fetch precedent (120 s) and `max_response_bytes=max_bytes`, every error re-raised through `_redact` (the URL carries the token); `set_message_reaction(chat_ref, message_id, emoji) -> bool` (`setMessageReaction`, `reaction=[{"type": "emoji", "emoji": …}]`), answering whether Telegram accepted it, since a group can restrict reactions. `send_text` passes `reply_parameters={"message_id": …}` when the payload carries `reply_to_message_id`; the outbox `send(row)` text fallback `:602-612` forwards it.
2. **The Drive write leg.** `google_drive_adapter.py`:
   - `folder_writable(*, workspace_id, folder_ref) -> Optional[bool]` — `files.get` with `fields=trashed,capabilities/canAddChildren`; `None` when the grant cannot see the folder (404), `False` when it is trashed or not writable.
   - `find_drop_folder(*, workspace_id) -> Optional[str]` — `files.list` with `q="appProperties has {key='storydump' and value='telegram_drops'} and appProperties has {key='workspace' and value='<ws>'} and mimeType='application/vnd.google-apps.folder' and trashed=false"`. Both properties, always: one Google account may back several workspaces, and a folder tagged for another is never this workspace's.
   - `create_folder(*, workspace_id, name, app_properties) -> str` — a POST under a policy with `max_attempts=1`, because the floor retries a POST whose answer was lost and a retry would make a second folder (the precedent is `telegram_transport.py:457-462`); `find_drop_folder` recovers the folder a lost answer made.
   - `find_file_by_app_property(*, workspace_id, parent, key, value) -> Optional[dict]`.
   - `upload_file(*, workspace_id, parent, name, mime_type, description, app_properties, data) -> dict` — resumable: a POST to `upload/drive/v3/files?uploadType=resumable&fields=<FILE_FIELDS>` with the metadata JSON → `Location` (also `max_attempts=1`), then a PUT of the bytes under the upload class with the 120 s budget; it returns the file resource with `FILE_FIELDS` (`:245`: id, name, mimeType, size, modifiedTime, md5Checksum), which is what the sync's upsert needs.
   - All five re-mint once on a refused token, as `_get_as_workspace` does. Errors classified by reason, as the adapter already does for reads: `storageQuotaExceeded` → a new `DriveFull`; rate limits → retryable; `insufficientPermissions` and 401 → the `DriveCredentialDead` class; 404 on the parent → a new `DriveFolderGone`.

6. **The executor.** `telegram_drops.relay_telegram_drop(deps, session, job) -> str`, registered in `build_registry` behind a wrapper marked `@own_transactions` (the shape of `work_loop.py:649-651`), so the loop calls it with `session=None`; parked by name when the transport or the Drive seam is missing (`TestRegistryCoversTheSchema`, `test_work_loop.py:123`, forces the entry); and added to `PROVIDER_FACING` (`test_work_loop.py:82-91`). It opens its own sessions with `unit_of_work.poller_session_factory(deps.engine, workspace_id)` and commits them itself, and it makes every provider call only after the session block has closed, because the in-transaction flag covers the whole block. Whenever it refuses, it writes the reply in the same transaction as `jobs.finalize_job` and returns `jobs.SELF_FINALIZED`, so a refusal is sent exactly once; it logs its outcome and a refusal's reason, and the reply's payload carries a machine-readable `reason`.
   1. In a session: read the workspace's live drop source (`provider='gdrive' AND config->>'role'='telegram_drops' AND NOT removed`, with `workspace_id = :ws`), the grant's scopes (`drive_credentials.grant_scopes`) and the payload; close the block.    2. With a source: `folder_writable` under the current grant. When the grant cannot see the folder or cannot write it — a reconnect under another Google account, a trashed folder — retire the role on the old row, which stays a connected folder and errors like any folder its grant cannot see, and continue as if there were no source.
   3. No source: `find_drop_folder` recovers a folder an interrupted attempt made, else `create_folder("Telegram drops", {storydump: telegram_drops, workspace: <ws>})`; then in one session `get_or_create_media_source(folder_ref=<id>, folder_name="Telegram drops")` with `role` in the config (`provisioning.py:530-534` gains an optional `role`), `rearm_after_connect(session, workspace_id=…, source_id=<the new source>)` — without `source_id` it re-arms every source (`media_sync.py:139-152`) — and the admit to the mix (F12); commit; close.
   4. `get_file`; `download_file(file_path, max_bytes=DROP_MAX_BYTES[kind])`; a file over the cap, when admission could not know its size, is refused.

In one session: upsert the item from the upload's file resource through the sync's own item upsert, factored out of `media_sync._land_page` so both callers share one statement (category and folder path as the sync would set them for a file directly in the drop folder); then mint the demand sync with `unless_pending=True` as a backstop, and, when `sent_as == "photo"`, the send-as-file hint (scope `drop_notice`, key `<ws>:<telegram id>:hint`, one a day); commit; close.
