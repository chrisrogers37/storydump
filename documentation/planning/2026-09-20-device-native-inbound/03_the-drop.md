## Summary

The dispatcher recognises a media message in a bound group from a linked member and enqueues one job in the delivery's own transaction. The job, on the interactive lane and serialized per workspace, finds or creates the workspace's "Telegram drops" folder in Drive (admitting it to the mix on creation), downloads the file from Telegram under the 20 MB bot cap, uploads it into the folder with Drive's resumable protocol, mints the same demand sync Sync Now mints, and reacts to the original message. Every refusal is one reply through the outbox, and the job then counts as handled. One migration adds the job kind. A compressed drop is accepted with a paced hint. Docs: the Telegram rules page, the webhook runbook, a new live guide, and the two post-ratification rulings in the design record.

### Steps

1. **Migration `scripts/migrations/NNN_relay_telegram_drop_kind.sql`**, NNN the next free number at build time (F9): `ALTER TABLE jobs DROP CONSTRAINT ck_jobs_kind;` then `ADD CONSTRAINT ck_jobs_kind CHECK (kind IN (<the sixteen>, 'relay_telegram_drop'))` in 065's layout; `ck_jobs_system_kinds` untouched (a tenant kind satisfies the biconditional as `false = false`); a postcondition reading `pg_get_constraintdef` for the new value. Mirror: the next free `### §` in `07-security-model.md` with the identical fenced block, its sha256 normative in `scripts/advertised_ddl_manifest.json`, the file in `tests/scripts/test_lineage_lane.py`'s ratified list, the normative-block count pinned at `tests/scripts/test_advertised_ddl.py:292` raised by one, `machinery.py:77-85` widened, `adoption_manifest.json` extended.
2. **Recognition.** `src/services/target/telegram_drops.py` (new): `Drop` (chat ref, message id, sender Telegram id, file id, unique id, size, mime, kind `image|video`, caption, `sent_as` `photo|video|file`) and `drop_of(update) -> Optional[Drop]`: a `message.photo` → the largest `PhotoSize`, `sent_as="photo"`; `message.video` → `sent_as="video"`; `message.document` whose `mime_type` starts with `image/` or `video/` → `sent_as="file"`; anything else, a DM, a channel post, a bot sender → `None`. The refusal and hint texts live here as constants.
3. **The dispatcher branch.** `telegram_dispatch.py:333-340`: after `_observe_all` returns for a group message, `drop = drop_of(payload)`; if present, `await telegram_drops.admit_drop(conn, drop, chat_type=…, chat_ref=…)`:
   - `tenant_resolution.resolve_chat` resolves the binding (`unknown_binding`/`revoked_binding` → nothing, as today); `identity.user_for_identity` (`identity.py:167`) resolves the sender; unlinked → one `notification` row for that binding through `outbox.enqueue`, the envelope `fanout_notification` builds plus `reply_to_message_id`, outcome `drop_unlinked`, no job.
   - Else `jobs.enqueue(session, kind="relay_telegram_drop", workspace_id, serialization_key=f"drop:{workspace_id}", lane="interactive", max_attempts=5, deadline_seconds=1800, payload={"v": 1, "binding_id", "chat_ref", "message_id", "sender_user_id", "sender_telegram_id", "file_id", "file_unique_id", "file_size", "mime_type", "kind", "caption", "sent_as"})` (F3; the deadline runs from mint, `jobs.py:343-344`, so time a drop waits behind an earlier one in the same workspace counts against it), `unless_pending=False` (every drop is its own job; the key serializes execution, not admission). Outcome `drop_enqueued`. The route's `conn.commit()` at `webhooks.py:250` commits it with the delivery. The size cap is applied here too: a `file_size` over 20 MiB is refused with the reply and no job.
4. **The transport.** `telegram_transport.py`: `get_file(file_id) -> dict` (`getFile`); `download_file(file_path, *, max_bytes) -> bytes` — GET `{_api_base}/file/bot{token}/{file_path}` through `egress.request` under `timeout_class="upload"`, `max_response_bytes=max_bytes`, errors re-raised through `_redact` (the URL carries the token); `set_message_reaction(chat_ref, message_id, emoji)` (`setMessageReaction`, `reaction=[{"type": "emoji", "emoji": …}]`). `send_text` passes `reply_parameters={"message_id": …}` when the payload carries `reply_to_message_id`; the outbox `send(row)` text fallback `:602-612` forwards it.
5. **The Drive write leg.** `google_drive_adapter.py`: `find_folder_by_app_property(*, workspace_id, key, value) -> Optional[str]` (`files.list` with `q="appProperties has {key='…' and value='…'} and mimeType='application/vnd.google-apps.folder' and trashed=false"`; under `drive.file` the app sees what it created); `create_folder(*, workspace_id, name, app_properties) -> str` (POST `files`, `mimeType` folder, no parent (F5)); `find_file_by_app_property(*, workspace_id, parent, key, value) -> Optional[str]`; `upload_file(*, workspace_id, parent, name, mime_type, description, app_properties, data) -> str` — resumable: POST `upload/drive/v3/files?uploadType=resumable` with the metadata JSON → `Location`, then PUT the bytes, both through the floor under the upload class; all four re-mint once on a refused token like `_get_as_workspace`. Errors: 401/403 → `DriveCredentialDead`-class (the grant cannot write); 404 on the parent → a new `DriveFolderGone`; else the existing retryable classes.
6. **The executor.** `telegram_drops.relay_telegram_drop(deps, session, job) -> str`, registered in `build_registry` behind a wrapper marked `@own_transactions` (the shape of `work_loop.py:649-651`), so the loop calls it with `session=None` and finalizes it in its own transaction; parked by name when the transport or the Drive seam is missing (`TestRegistryCoversTheSchema`, `test_work_loop.py:123`, forces the entry); and added to `PROVIDER_FACING` (`test_work_loop.py:82-91`). It opens its own sessions with `unit_of_work.poller_session_factory(deps.engine, workspace_id)` and commits them itself, and it makes every provider call only after the session block has closed, because the in-transaction flag covers the whole block:
   1. Read the workspace's drop source (`provider='gdrive' AND config->>'role'='telegram_drops'`), the grant's scopes (`drive_credentials.grant_scopes`), and the payload. Refuse when not writable, when the source is removed (`config->>'removed'`), or when the grant is not active: in the same session, one notification with `reply_to_message_id`; commit; close the block; return `"drop-refused"`.
   2. No source: outside any transaction, `find_folder_by_app_property(storydump=telegram_drops)` else `create_folder("Telegram drops", {storydump: telegram_drops, workspace: <ws>})`; then in one transaction `get_or_create_media_source(folder_ref=<id>, folder_name="Telegram drops")` with `role` written into the config (extend the config JSON at `provisioning.py:530-534` with an optional `role`), `rearm_after_connect`, `category_mix.admit_source(source_id)`; commit.
   3. `get_file` → refuse on Telegram's too-big answer; `download_file(file_path, max_bytes=20 MiB)`.
   4. `find_file_by_app_property(parent, telegram_file_unique_id, <id>)`; if absent, `upload_file(...)` named per F2 with the description "Dropped by <name> in <group> on <date>" plus the caption and the app properties `{telegram_file_unique_id, telegram_chat, telegram_message, dropped_by}`. `DriveFolderGone` → refuse naming the restore or the removal; a dead grant → refuse naming the reconnect (each refusal: open a session, write the notification, commit, close, return `"drop-refused"`); retryable → raise.
   5. In one transaction: `jobs.enqueue(kind="sync_media_source", serialization_key=f"src:{source_id}", payload={"v": 1, "source_id", "reason": "demand"}, unless_pending=True)` (the `sync_now` shape); when `sent_as == "photo"`, `rate_counters.increment(scope="drop_hint", key=f"{ws}:{sender}", window_start=window_start(now, 86400), limit=1)` and, when it answers 1, one notification with the hint; commit.
   6. `set_message_reaction(chat_ref, message_id, <F1>)`; a failure is logged, not retried; return `"relayed"`.
7. **Docs.** `.claude/rules/telegram.md` gains "Inbound: a drop" between the dispatcher and the card; `documentation/operations/telegram-webhook.md:150-152` says drops rely on the same precondition membership does; `documentation/guides/media-sources.md` (new, a live page): Drive folders, Telegram drops (how to drop, the reaction, send-as-file, the 20 MB cap, curation by dragging, the 20% share), with a row in `documentation/README.md`; `03-decision-record.md`, post-ratification rulings: D37's write leg and the 2026-09-05 scope amendment, both citing the decision doc. The docs guard battery green.
8. **CHANGELOG** under Unreleased.

## What NOT To Do

No provider call inside the webhook's transaction. No DM path. No second drop folder per bound group. No `unless_pending` on the relay enqueue. No storing of bytes anywhere but Drive. No reaction before the file has landed.
