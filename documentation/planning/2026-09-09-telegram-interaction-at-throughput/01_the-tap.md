# Phase 1 — The tap

> **COMPLETE — built 2026-09-09 as [#1271](https://github.com/chrisrogers37/storydump/pull/1271)** (branch `implement/telegram-tap`). Build-time adjustments (codebase comparison): (1) the unlinked tapper's alert names the web path ("Link your Telegram account first: Settings › Integrations") — a `link` start token is minted for a signed-in web user and the tapper is by definition unknown, and `answerCallbackQuery`'s `url` is for games only, so no URL and no DM card; (2) `settled_by` shows the tapper's Telegram display name (what the group already sees; `user_identities.display_name`), else the sign-in display name, never an email — there is no per-workspace display name; (3) `outbox.deliver` keeps its never-commits contract (the sender gate pins that a fenced finalize rolls the write back); the checkpointing lands in `OutboxPoller.tick`, the production path: pace-and-claim, commit, send, settle, commit.

## Summary

A tap on `🚀 Post now`, `✅ Posted myself`, `⏭️ Skip` or `🚫 Reject` reaches the command port as the tapping member, flips the intent in one transaction, is answered within the ingress budget, loses its buttons at once, and gets the outcome line through the outbox. A second tap on the same card, a tap by someone else after the first, or a tap on a finished card answers with the card's current state and writes nothing. Cards end in every terminal state, not only the tapped ones. The sender commits its claim before the provider call so a tap never waits on an upload. Telegram is asked for taps at all: the webhook is re-registered with `callback_query` and a deliberate `max_connections`. This is the W4 inbound half (`01` §1; `02` §5); it closes #1040 and #1260 and settles #854's tap half (#854 stays open for typed commands). Phase 1 alone satisfies "build for 2 teams today".

### Steps

1. **Tests first** (see Test Plan) — unit tests for the registration constant, the parser, the transport methods and the dispatcher branch; executor tests for the read-then-decide flip; sender-gate tests for the checkpointing; a W4 gate `tests/scripts/test_w4_tap_gate.py` (new) on the Docker database.
2. **Registration.** `scripts/telegram_webhook.py:60` → `ALLOWED_UPDATES = ["message", "callback_query"]` (and the comment at `:57-59` says why); `register` (`:245-254`) sends `max_connections` from `TARGET_TELEGRAM_WEBHOOK_MAX_CONNECTIONS` (default = ingress workers × `POOL_SIZE_SEAM`, 10 today, 20 if F5 locks (a)); `verify` already prints `allowed_updates` and `pending_update_count` (`:192-194`). Deploy step: re-run `register` after the phase 1 deploy; checklist item below. Runbook amended.
3. **Parser.** New `src/services/target/callback_tokens.py`: `parse(callback_data: str) -> Tap | None` returning `Tap(version=1, action, intent_id)`; refuses anything but `v1:` with the known actions and a UUID; `prompts._token` moves here (imported back into `prompts`) so mint and parse are one module. If F10 locks (a) the action set gains `reject_confirm` and `keep` (`v1:reject_confirm:<uuid>` / `v1:keep:<uuid>`, within 64 bytes) and `render_card` gains the confirm keyboard and the row-1 layout the fork rules.
4. **Transport.** `TelegramTransport.answer_callback(callback_query_id, text, *, show_alert=False, url=None, timeout_s=2.0)` → `answerCallbackQuery` (best effort: log on failure, never raise past the route; `url` carries the `link` start URL for the unlinked tapper); `edit_reply_markup(chat_ref, message_ref, reply_markup)` → `editMessageReplyMarkup`; `edit_caption(chat_ref, message_ref, caption)` → `editMessageCaption`; `edit_text(chat_ref, message_ref, text)` → `editMessageText`. The 400 "message is not modified" answer is success for all three edits.
5. **The card edit (F4 (a)).** `mark_sent` gains `sent_as` (`"media"` or `"text"`, returned by `for_chat().send` beside the ref) written into the row's JSONB payload — no migration. `supersede_all` gains `outcome_text` and copies the superseded row's header (`caption` or `text`) and `sent_as` into the `prompt_supersede` payload. `for_chat().send` learns the kind: `editMessageReplyMarkup(empty)` on `supersedes_ref` first — type-agnostic, the call that must land — then, when the payload carries `outcome_text`, `editMessageCaption` for `sent_as == "media"` else `editMessageText`, with **the original header plus the outcome line** (`📸 @handle` / slot kept; `✅ Approved by Chris · 2026-09-09 14:14` appended); a 400 on the second call is logged, never fails the row. A supersede row without `outcome_text` still strips the keyboard, so no `prompt_supersede` payload can hit the no-`text` failure at `telegram_transport.py:369-373`. The outcome line and the slot line share one formatter in `prompts` (`%Y-%m-%d %H:%M` + tz, `prompts.py:103`).
6. **Read-then-decide executors (F2 (a)).** `_intent_row` gains `FOR UPDATE OF i`. A new `_settle(intent, action)` returns an `answered` `CommandResult` (`{intent_id, state, settled_by, settled_at}`) whenever the row is in **any state other than `awaiting_approval`** — the same rule as `mark_posted`'s CTE — so `review_required` (the operator's edge, `055:303`), `publishing`, every terminal state and a repeat of the same action all answer and write nothing; `approve`, `skip`, `reject`, `mark_posted` call it before `_flip`. The guard's `illegal_transition` remains the answer only for an edge the guard refuses on a row that *was* `awaiting_approval` at read time (it should never fire; it is the last line). `settled_by`/`settled_at` come from the newest `audit_events` row for the intent (`ix_audit_entity`, `055:209`, bound on `workspace_id`, ordered `id DESC`) — one indexed read; `settled_by` renders the member's workspace display name, never an email-derived string. `_settle` also enqueues the supersede for the tapped card (step 7) so a stale card heals on first touch.
7. **Supersede across every binding, in every terminal state.** After a successful flip each executor calls `outbox.supersede_all(…, outcome_text=…)` for **each** binding from `prompts.push_bindings(session, workspace_id)`; the rows are in the flip's transaction, so a rolled-back flip takes its edits with it. `supersede_all` now targets `sending` too (step 8 makes that a committed state). The same call, with the terminal line, is added to every writer that ends an intent: `reap_expired` (`work_loop.py:206`: `⌛ Expired — slot passed`), `cancel` and the reaper leg it hands to (`command_executors.py:291`, #1235: `🚫 Cancelled`), `disable_account` (`:409`: `⏸ Account disabled`), and the pipeline's `posted` write (`publish_pipeline.py:876`: `✅ Posted to @handle`) — `06:49`'s "cards for it supersede with a notice", made real.
8. **The sender commits before the call (F8 (a)).** `outbox.deliver` becomes transaction-per-checkpoint (`02:1254`): the two `increment` debits and `claim_next` commit together *before* `transport(row)` (a claim that finds nothing rolls the debits back); `mark_sent`/`mark_ambiguous`/`_leave_sending` run in a fresh transaction afterwards with the GUCs re-applied (`poller_session_factory`, `work_loop.py:673-689`, applies them per transaction). The `tg_global` row is never locked across the provider call — #1260 closes here. After the send, whether `mark_sent` succeeds or is fenced (`OutboxFenced`: the row was superseded while in flight, its ref unknown to the supersede), the sender re-reads the intent's state (R6) and, when it is in neither `prompt_pending` nor `awaiting_approval`, enqueues `prompt_supersede` for the ref it just received with the outcome line; a duplicate edit answers "not modified", which is success.
9. **Dispatcher branch.** `TelegramDispatcher.__call__`: when `payload["callback_query"]` exists → `_tap(conn, payload)`: parse the token (unknown → answer "This button is from an older card" and stop); `resolve_chat("telegram", str(message.chat.id))` (unknown/revoked → answer "This chat is not connected to a workspace"); the per-workspace admission check when phase 2 lands (before any write; F12); `user_for_identity("telegram", str(from.id))` (None → the unlinked answer with the `link` start URL, or a one-button link card to the tapper's DM through the outbox — F3 (a)); `commands.execute(conn, Command(kind, workspace_id, user_id, "telegram", {"intent_id": …}))` with `apply_gucs(actor_kind="user", actor_user_id, channel="telegram")` on the connection; map `TenantResolutionError` (not a member / below floor) and `CommandRefused` to answers; return `TapResult(handled=True, callback_query_id, message_ref, answer_text, show_alert, outcome)`. **Never raise**: a `callback_query` without `message`, a missing field, any non-database exception is caught here, the outcome set to `tap_failed`, logged at ERROR with `update_id`, counted on `/health` — the delivery stays admitted, as `_observe_all` does at `:107-111`. Only a database error around commit escapes to the route (phase 2 maps it to 503).
10. **Answer and strip after commit.** `webhooks._acknowledge` grows the callback case: when the result carries `callback_query_id`, `runtime.answer_callback(id, text, show_alert, url)` (a new optional `IngressRuntime.answer_callback`, wired in `app.py` beside `reply`) and, beside it, `runtime.strip_keyboard(chat_ref, message_ref)` → an unpaced best-effort `editMessageReplyMarkup(empty)` on the tapped message only (its ref is the callback's own `message`, so the known-ref rule holds). Outside the connection, after the commit, best effort, one answer per query. The paced supersede rows still write the outcome line in every binding.
11. **Action → command mapping and the `ANSWERS` table.** `post → approve` (requires `api_publishing_enabled`; otherwise `manual_mode` → "This workspace posts by hand — tap Posted myself after posting"), `posted → mark_posted`, `skip → skip`, `reject → reject` (or `reject → confirm keyboard`, `reject_confirm → reject`, `keep → restore keyboard` under F10 (a)). One `ANSWERS` table in `telegram_dispatch` keyed on outcome and `CommandRefused` reason — executed (`post`: "✅ Approved — posting shortly", or until #1220 step 3 lands "✅ Approved — publishing isn't live yet; it will post when it is" per F11; `posted`: "✅ Marked posted"; `skip`: "⏭️ Skipped for 30 days"; `reject`: "🚫 Rejected"), answered ("Already approved by Chris · 2026-09-09 14:14", state-specific), refused (`not_found`, `manual_mode`, `cancelling`, `illegal_transition`, not a member, below floor, suspended workspace, unlinked, not connected, older card, rate-limited, `tap_failed`), with a fallback "Couldn't do that — open the queue on the web". `show_alert=True` for the refusals the tapper must act on: unlinked, not connected, manual mode, rate-limited, older card. A test asserts every reason the executors and the resolver can raise has an entry.
12. **Observability.** One structured log line per tap (`update_id`, workspace, action, outcome, ms-to-commit, ms-to-answer) and counters on `/health` (`taps_total` by outcome, `tap_failed`, `answer_failed`, `strip_failed`).
13. **Docs.** `02` §5 amendment: the tap's read-then-decide rule, the supersede-across-bindings rule, the sender's transaction-per-checkpoint; `02` §6: cards end in every terminal state; `06` §5 (customer-visible behaviour, `06:63`): what each tap answers and shows; `03` post-ratification ruling with the locked forks; CHANGELOG entry; the `.claude/rules/telegram.md` table gains the target-tier tap (the file describes the legacy bot today); `documentation/operations/telegram-webhook.md` gains the `callback_query`/`max_connections` note.

## What NOT To Do

- Do not call Telegram inside the flip's transaction, and do not hold the sender's transaction across the provider call.
- Do not admit the update a second time through `commands.ingest`; the webhook's `update_id` admission is the ledger.
- Do not answer a tap 200 without either executing or answering it by name; do not answer a query twice.
- Do not raise out of `_tap` for anything but a database error; a poisoned update must be a named outcome.
- Do not let a member's tap take any edge but `awaiting_approval → <action>`.
- Do not edit a card whose message ref is unknown; do not replace the card's header with the outcome.
- Do not say "posting shortly" while the publish leg is parked (F11).
