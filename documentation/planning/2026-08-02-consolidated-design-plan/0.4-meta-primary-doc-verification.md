### 1. Publish cap — confirmed at 100 / rolling 24 h

**CP**, verbatim:

> Instagram accounts are limited to 100 API-published posts within a 24-hour moving period.
> Carousels count as a single post. This limit is enforced on the POST /<IG_ID>/media_publish
> endpoint when attempting to publish a media container.

`05`'s row 13 stands as written. Two additions worth carrying:

- **carousels count as one post** — not previously recorded here, and it matters to any local
  estimate;
- **Meta's own two pages disagree on the number.** **CPL** describes `quota_total` as
  *"The maximum number of IG Containers the app user can publish within the `quota_duration` time
  period (currently 50)"*. So the guide says 100 and the endpoint reference says 50, today, on the
  same vendor's site.

That disagreement is not a problem to resolve — it is the argument for the rule already in the
code. A constant copied from either page is wrong for some account at some time; the live
per-account `content_publishing_limit` read is the only arbiter, which is exactly what `main`
does. It is also the second time this figure has drifted (#734 was the first), which is why the
docs below now point at the live value rather than restating a number.

### 2. Platform call rate — the figure is right, the shape is not

`05` row 14 carries *"200 / user / hr"* as an unverified second-hand input. **RL**, verbatim:

> Calls within one hour = 200 * Number of Users

> The Number of Users is based on the number of unique daily active users an app has.

This is an **app-level pool sized by daily active users**, not a per-user ceiling. The difference
is load-bearing in both directions: one user may exceed 200 calls in an hour while the app stays
inside its budget, and an app with few daily active users has a *smaller* total budget than
"200 × registered accounts" would suggest. A capacity model that reads it as a per-user allowance
will over-estimate headroom exactly when the user base is quiet.

### 3. Instagram-Login scopes and refresh semantics — confirmed, min-age is 24 h

Scope names, from **CP**'s requirements block for Business Login for Instagram:
`instagram_business_basic`, `instagram_business_content_publish`. These match
`src/services/integrations/instagram_login_oauth.py` exactly.

**BL** on refreshing a long-lived token, verbatim — the token is extended

> for another 60 days as long as the existing conditions are true: The existing long-lived access
> token is at least 24 hours old   The existing long-lived access token is valide (not expired)
> The app user has granted your app the instagram_business_basic permission

and

> Tokens that have not been refreshed in 60 days will expire and can no longer be refreshed.

Endpoint: `GET https://graph.instagram.com/refresh_access_token` with `grant_type=ig_refresh_token`.

**The min-age rule is 24 hours, and `05`'s refresh cadence clears it.** Row 56 schedules refresh
every 7 days from issue, jittered — 7 days is comfortably outside the 24-hour floor, so the
decoupling from expiry proximity introduces no eligibility conflict. This was the open question
the row flagged; it is now closed rather than assumed.

Note the third condition: refresh eligibility depends on `instagram_business_basic` still being
granted. A scope revocation therefore presents as a refresh failure, which is consistent with
treating a definitive auth rejection as a liveness signal (D31) rather than a transient error.

### 4. Usage-endpoint shape — `available_at` is not exactly derivable

`02` §8 marks this uncertain. It resolves to: **the shape does not carry what an exact derivation
needs.** **CPL** documents:

- `config` → `quota_total`, `quota_duration` (*"currently 86400 seconds, or 24 hours"*);
- `quota_usage` → *"The number of times the app user has published an IG Container since the time
  specified in the `since` query string parameter"*;
- `since` → *"A Unix timestamp no older than 24 hours."*

`quota_usage` is a **count**, never a list of publish timestamps. The oldest-publish instant that a
next-free-slot calculation needs is not exposed, so §8's stated fallback — conservative deferral to
the account's next product slot — stands unchanged.

One nuance worth recording rather than discovering later: because `since` accepts any timestamp
inside the window, the oldest publish *could* be located by repeated probing. That is a **bounded
search, not a read** — it costs several calls per derivation, which collides with §8's own budget
of at most one query per publish attempt. So it is not a route to the exact value at acceptable
cost, and the fallback remains correct. Correctness never depended on this anyway: error 9
re-arbitrates on every attempt.

### 5. Container status vocabulary — the premise was wrong, and the seam resolves to container-verdict

This was the load-bearing question. `04` §0.4 and `02` §6 both record the premise that Instagram
documents `FINISHED` as pre-publish while `PUBLISHED` belongs to Threads, raising the possibility
(R3 review §6.11, *marked uncertain, not false*) that the pass-2 contract borrowed its authoritative
evidence from the wrong API.

**It did not.** **CP** — Instagram's own content-publishing guide — documents five values on
`GET /<IG_CONTAINER_ID>?fields=status_code`, verbatim:

> EXPIRED — The container was not published within 24 hours and has expired.
> ERROR — The container failed to complete the publishing process.
> FINISHED — The container and its media object are ready to be published.
> IN_PROGRESS — The container is still in the publishing process.
> **PUBLISHED — The container's media object has been published.**

`PUBLISHED` is documented for **Instagram** containers, not only for Threads. A post-publish
observable terminal status therefore exists, the authoritative-positive set is non-empty, and the
`reconciler_evidence_mode` seam resolves to **container-verdict mode**.

Seam values as set, following §6's definition (which value is authoritative *after*
`publish_called`):

- **authoritative-positive:** `PUBLISHED`
- **authoritative-negative:** `EXPIRED` (the 24-hour window closed without a publish), `ERROR`
  (*"failed to complete the publishing process"*)
- **non-terminal:** `IN_PROGRESS`; and `FINISHED`, which after `publish_called` means *ready to be
  published* — i.e. evidence the publish has not landed, not evidence that it failed. Treating
  `FINISHED` as authoritative-negative would be the trap here.

**CP** also states a polling recommendation this repo should honour: *"We recommend querying a
container's status once per minute, for no more than 5 minutes."* `05`'s ladder (60 s → 5 m → 30 m
→ 2 h, capped at container expiry) is *more* conservative than that after the first rung, so it
does not conflict — but Meta's guidance is bounded at 5 minutes and the ladder runs to ~24 h, so
the long tail is our extension rather than Meta's advice.

### 6. Stories-list lookback — 24 h confirmed, with two exclusions that matter

**ST** documents `GET /{ig-user-id}/stories` → *"Returns a list of story IG Media objects on an IG
User."* Under Limitations, verbatim:

> Responses will not include Live Video stories. Stories are only available for 24 hours. New
> stories created when a user reshares a story will not be returned.

The 24-hour lookback is confirmed. The two exclusions are new here and bear directly on `02` §6's
exhaustion tail, which uses a **final stories check** as evidence before parking `review_required`:
that check is not a complete view of what the account posted. A story absent from the list is not
proof it was never published. In container-verdict mode this matters less than it would have in
evidence-capture mode, but the tail still runs, and the check should be read as corroborating
rather than dispositive.

### 7. URL-pull only — contradicted; a push-bytes surface exists

`04` §0.4 asks to confirm *"that publishing remains URL-pull only (container creation takes
`image_url`/`video_url`; no push-bytes surface — the premise of the D38 transit analysis)."*

**Half of it holds.** For images, **CP** is explicit: `image_url` or `video_url` is
*"Set to the path of the image or video. We will cURL your image using the passed in URL so it must
be on a public server."* That is URL-pull, and the D38 transit analysis rests on it correctly for
the image path.

**For video it does not hold.** **CP** documents a resumable upload session against a separate
host:

> Most API calls use the graph.facebook.com host however, calls to upload videos for Reels use
> rupload.facebook.com . The following file sources are supported for uploaded video files:
> **A file located on your computer** A file hosted on a public facing server, such as a CDN

and, in the upload step:

> Be sure the host is rupload.facebook.com . **All media_type shares the same flow to upload the
> video.**

So a push-bytes surface exists (`POST https://rupload.facebook.com/ig-api-upload/<CONTAINER_ID>`),
it accepts a local file, and Meta's own wording says all media types share that flow — while the
surrounding sentence frames it as the Reels path. Meta is ambiguous about the exact scope; it is
**not** ambiguous about whether pushing bytes is possible.

**What this does and does not mean for D38.** It does not invalidate the current design: the
URL-pull path is still fully supported and is what this product uses, so the transit analysis's
conclusions about hosting media at a public URL stand on their own merits. What changes is that
"no push-bytes surface exists" can no longer be cited as a *premise* — the option exists, and if
transit cost is ever revisited (D38's stated trigger is sustained Cloudinary consumption above 225
credits), direct upload is a real alternative that the analysis currently rules out by assumption
rather than by argument.

## On #734, which named the wrong defect

#734 reports that three docs *"state the stale 25/24h Instagram publish cap"* and asks for them to
say 100. Checked against the tree at `c11f614`, that is not what they say, and two of its three
premises have drifted:

- `documentation/guides/instagram-api-setup.md` **no longer exists** — deleted in `08a8ed5` (#738).
- The two survivors state *"25 posts/**hour**"*, not a 25-per-24-hour cap, and both attach it to
  the env var `INSTAGRAM_POSTS_PER_HOUR` — which **was renamed** to
  `INSTAGRAM_PUBLISH_LIMIT_FALLBACK` in #707 (`99b00ea`) and no longer exists anywhere in the tree
  outside CHANGELOG history.

So the operator-facing defect is worse than a stale number and different in kind: the docs describe
a per-hour throttle that was deleted, and point at an environment variable that will not resolve.
Writing "100" into them, as filed, would have produced a confidently wrong sentence — a correct
figure attached to a removed mechanism. They are corrected to describe the mechanism that actually
runs: a live per-account rolling-24 h quota read from Meta, with `INSTAGRAM_PUBLISH_LIMIT_FALLBACK`
(default 100) as the fail-open fallback.

## What this pass did not establish

- **Whether the `rupload` push path is genuinely available for `STORIES` media_type**, which is
  what this product publishes. Meta's page says both *"calls to upload videos for Reels use
  rupload.facebook.com"* and *"All media_type shares the same flow"*. Settling it needs an API
  call against a real container, which is outside a documentation-only item. Item 7 above is
  therefore stated as *a push-bytes surface exists*, not as *it is available to us for stories*.
- **The `quota_total` divergence (50 vs 100) is reported, not adjudicated.** Both are Meta's own
  current pages. Which one a given account actually gets is precisely what the live read answers,
  so no adjudication is needed for correctness — but nobody should cite either page as *the* number.
- Verification covered the seven checklist items in #745. Other platform facts in `05` were not
  re-verified in this pass.
