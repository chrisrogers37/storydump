# Execution sequence

The single consolidated sequence (G6): it supersedes `epic.md`'s phases, `implementation-plan.md`'s ordering, and #721's roadmap. Each increment names the #722 items it absorbs (**TT:P0-nn / P1-nn**, from `../2026-07-29-high-throughput-multi-tenant/tiered-issue-triage.md`) so the ratified gate rigor is traceable — **these markers are audit annotations, not required reading: every increment's scope and exit gate is stated in full in this file**. Where an absorbed item had a Redis half, that half is struck per C3 and the replacement named. Increments are PR-sized; an increment ships only when its **exit gate** passes.

**Fifth pass (FC-7, 2026-08-04): the migration is an offline cutover.** The product owner ruled a days-scale window with hand re-authentication, so every mechanism that existed **only** to keep two live systems agreeing is deleted — the §Superseded pass-5 strikes line below is the authoritative enumeration. Deleted increments carry explicit tombstones rather than silent removal, so a stale cross-reference is detectable. The build order becomes: **Phase 0 (external dependencies + rails) → Phases F/L (build the target system; production untouched) → Phase M (the rehearsed cutover window) → Phases X/S (post-cutover features and scale proofs).**

## Ground rules (apply to every increment)

- Documentation-only until Phase 0's safety rails exist. No production migration runs before 0.2's runner ships — and no production schema or data change happens outside the M.3 window, **with exactly two named exceptions (pass 6 — R5 P2: the rule and 0.3 contradicted each other): 0.3's `posting_history` duplicate cleanup + `UNIQUE(queue_item_id)` validation, and the media-hash dedup remediation.** Both are human-gated remediations of known legacy defects whose cleanliness the M.1 transform's correctness depends on; they run **before** the window precisely so the window's transform meets clean inputs with the human gate unhurried, they ride the 0.2 runner, and they are the complete list — a third pre-window production change is a review-blocking defect, not a precedent.
- Every schema change rides the numbered-SQL runner with postconditions + replay-from-empty CI (0.2). The target schema is authored as runner migrations from F.2 on; production first executes them inside M.3.
- Tables are born workspace-keyed, RLS-enabled, composite-FK'd — **at creation** (`02` §7 prints the enablement and policies in the same replay stream as the tables; there is no later "RLS completion" pass).
- Rollback statement required per increment PR (what flips off, what data survives).
- **The offline transform (single normative statement — FC-7; replaces the six-stage machine):** the legacy→target re-key happens **once**, inside the M.3 window, as runner-executed transform migrations authored from the `02` §9 mapping and specified per table in M.1. Rules that carry over from the struck machine because they are transform-correctness rules, not liveness machinery: naive legacy timestamps convert with `AT TIME ZONE 'UTC'` (`02` §0 — a bare cast fails review; the three already-`TIMESTAMPTZ` columns copy as-is); transforms run batched (initial batch 5,000 rows, config seam per `05` discipline) with a stop-on-violation rule; **every transform is rehearsed on a Neon branch before the real window (M.2)**; and **before any legacy table is dropped, the window snapshots it into the in-database archive schema** (`CREATE TABLE archive.<table>_pre_cutover_<YYYYMMDD> AS TABLE legacy.<table>` — legacy tables live in the `legacy` schema from M.3 step 3c on; **the date suffix is load-bearing**: it is what lets the one `02` §7-DDL archive retention mechanism age both name families with a single name test; owned by the snapshot migration running as `svc_migration`, then `ALTER … OWNER TO svc_maintenance` so retention can drop it; retention per `05` §DR; restoring beyond the snapshot's content is the declared non-goal it always was).
- **Version-skew rule (N-1), retained as target-system deploy hygiene:** all JSONB payloads carry `v`; every reader accepts `v` and `v-1`; a deploy may roll worker and ingress replicas in any order within one version window. Payload shape changes ship reader-first. (The rule's former second job — old and new *systems* against mid-track schemas — died with the six-stage machine.)

**0.2 Migration runner formalization (C6; absorbs TT:P0-01).** The numbered-SQL practice — today manual `psql -f` with self-stamping files; **no runner program exists on `main`** (pass-4 anchor) — becomes a real program with a real contract:
- **Ledger:** `schema_migrations(version INT PK, checksum TEXT NOT NULL, applied_at TIMESTAMPTZ NOT NULL DEFAULT now(), applied_by TEXT NOT NULL, execution_ms INT, status TEXT CHECK (status IN ('applied','repaired','adopted')))` — tooling meta-schema, deliberately homed here with the runner spec (the one exemption from `02`'s domain-DDL mandate); supersedes `schema_version` (which is archived at M.3). **Physical home: a dedicated `runner` schema (`runner.schema_migrations`), created by the runner itself at first contact, never `public` (pass 6 — R5 P0 consequence): M.3 step 3c renames `public` wholesale, and a ledger living there would ride into `legacy` mid-run, severing the migration history from the very invocation writing it. The runner schema is invariant across every schema-level operation, identically in CI and production.** Checksum = SHA256 of the file; an edited applied file is a **hard failure** (fix-forward with a new migration, never edit history); `runner repair --version N --reason …` records a deliberate exception as `status='repaired'`.
- **Production adoption (`runner adopt` — pass 5, closing R4's gap):** the command by which the live database, which predates the ledger, enters it. For each already-applied numbered file the adoption manifest pairs the file with a **live postcondition** (SQL returning bool — a table/column/constraint probe); `runner adopt` verifies each postcondition against production, seeds the ledger row (`status='adopted'`, checksum of the file as it exists in-tree), and **hard-fails naming the discrepancy** on any postcondition miss — it never trusts file order or the old `schema_version` rows (whose 010/034 gaps are exactly the hazard: R4's replay reproduced 47 rows with those two absent). Runs as the first act of M.3, after rehearsal on the M.2 branch.
- **Login (pass 8 — R7's PG16+ finding, the actor/ADMIN contract stated):** the runner's login `svc_migration` is created here, at 0.2 setup, **by the database-owner actor — the same role that later runs the M.3 step-0 bootstrap.** That identity is load-bearing across PostgreSQL versions: on 16+ a role grant requires the grantor to hold `ADMIN` on the granted role, and the *creator* receives `ADMIN` automatically — so same-actor creation is exactly what keeps the bootstrap's transient self-grant legal there (on the pinned PG15, `CREATEROLE` alone suffices; R7 executed the 16+ failure on 17.7: `permission denied to grant role`). A `svc_migration` created by any other actor must be granted to the bootstrap actor `WITH ADMIN OPTION` before the window; M.2's bootstrap leg is where a miss surfaces, on a branch. **The creator-ADMIN rows this contract produces persist on PG16+ by design (pass 9 — R8): PostgreSQL records their grantor as the cluster role, so the database owner cannot remove them at stand-down — the step-8 gates name them as the sole tolerated exception, pinned to their exact shape (`admin_option` only, no set, no inherit).**
- **Locking:** the runner takes `pg_advisory_lock(<fixed key>)` for the whole run — concurrent deploys serialize; second runner finds versions applied and no-ops. This is the deploy-locking answer (review A §5.16): Railway predeploy runs the runner; two services deploying concurrently cannot interleave DDL.
- **Transactions:** one migration = one transaction, except files carrying the `-- runner:no-transaction` marker (required for `CREATE INDEX CONCURRENTLY`); such files must be idempotent (`IF NOT EXISTS` discipline) since a mid-file crash leaves them partially applied.
- **Postconditions:** each migration may declare `-- runner:postcondition <SQL returning bool>` lines, executed after apply; false = failed migration.
- **Chain reconciliation (fix-forward for the known defects):** migration 050 drops the 004/008 orphaned unique if present (`ALTER TABLE api_tokens DROP CONSTRAINT IF EXISTS api_tokens_service_name_token_type_key` — the *actual* auto-generated name) and normalizes `chat_settings.caption_style` to TEXT (the divergence is model `String(20)` vs migration 030's `TEXT`; the live type depends on whether an install ran `init_db` or the migration first, which is exactly why 050 normalizes rather than assumes; pass-4 anchor) — after which replay-from-empty equals production. The missing 010/034 ledger entries are handled by `runner adopt`'s postcondition-verified rows, not by stamping the legacy table. **Precondition, before writing 050:** `\d api_tokens` and `\d media_posting_locks` against production to confirm the file-derived residue analysis.
- *Gate:* CI replays all migrations from empty — **extended stepwise to the M.3 lineage as its files land (pass 6 — R5 P0; actor-faithful pass 7 — R6 P0): today legacy setup + 001–050, then the 3c schema-move file, then the F.2 target files (= window steps 3b–3d) in one run; the M.1/snapshot/drop files (3e–3g) join the same run as Phase M writes them. The full-lineage replay is the window's step-3 sequence executed in CI **under the window's actors**: the lineage seeds under a database-owner-shaped actor (non-superuser, CREATEROLE — so the legacy tables carry *real legacy ownership*, not the gate runner's), the M.3 step-0 bootstrap runs as that owner, and every window step runs as `svc_migration` — so both collision classes found by hand-replaying (R5: target `CREATE TABLE` meeting a populated `public`; R6: the window failing under its own declared actor) fail in CI, not in the window**; a deliberately-broken parity fixture fails loudly; replayed-schema == models-schema parity test green (catches DB-only indexes/defaults drifting); **named fixture `advertised_ddl_replay` (pass 3; widened pass 5; redefined pass 6; actor-split pass 7; per-path stand-down shape pass 8; identity-gated pass 9): extracts and expands the advertised stream per its `02` §0 definition (the one normative home — literal blocks minus illustrative examples plus the §7-DDL normative-list policy expansions), then (a) replays the expanded stream from empty under the same actors as the full-lineage replay above (bootstrap as the owner actor, stream as `svc_migration`; `02` §0 owns the failure rule), asserting behavior, not just syntax: one legal intent transition succeeds, one illegal transition raises, `pg_policies` matches the normative lists, and the end state carries no door-owner `CREATE` on `public` (the stream's transient bracket closed behind itself) — (b) asserts the concatenated F.2 migration files equal the expanded stream by mechanical diff, so the gate tests exactly what F.2 installs — and (c) replays both M.3 step-8 stand-down variants and asserts their printed per-path gates — identity first, then shape, with the membership lines on the running major version's branch (pass 9): the success arm after the full window, the abandon arm after the four rollback legs, and both mis-runs REFUSED by the subject-identity guards with the schema untouched (R7/R8: a gate must observe, and verify, its own subject; this is where the both-exits closure is machine-checked, not just rehearsed)** (the behavioral half is the R4 class — a printed matrix with unseeded edges rejected every transition while replaying green; the lockstep half is the R5 class — a fixture that could not be both "verbatim" and complete); Neon PITR window ≥ the `05` §DR floor verified and recorded; `runner adopt` proven against a production-shaped fixture (all postconditions pass; --    out-of-band — never DDL). Guarded: pre-existing roles (svc_migration has been the
--    runner's login since 0.2) pass through untouched.
DO $$
DECLARE r text; own text;
BEGIN
  FOREACH r IN ARRAY ARRAY['svc_ingress','svc_worker','svc_migration'] LOOP
    IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = r) THEN
      EXECUTE format('CREATE ROLE %I LOGIN', r);
    END IF;
  END LOOP;
  FOREACH r IN ARRAY ARRAY['svc_claim','svc_clock','svc_maintenance','svc_membership'] LOOP
    IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = r) THEN
      EXECUTE format('CREATE ROLE %I NOLOGIN', r);

  --    OWNER TO mechanics that force it; revoked at step 8).

  --    svc_migration, and schema ownership does not confer table access (R6). Granted while
  --    the lineage still sits in public — grants attach to tables and ride the 3c rename.
  --    Closure, both exits (D40): on the success path they die with the tables at 3g; on
  --    the abandon path they survive the un-rename, and step 8's abandon variant revokes them.
  GRANT SELECT ON ALL TABLES IN SCHEMA public TO svc_migration;

  --    database CREATE. PG15 mechanics make the ALTER itself membership-gated, so the owner
  --    actor self-grants first (revoked at step 8; legal on PG16+ because the 0.2 login
  --    contract makes this actor svc_migration's creator, hence ADMIN holder). The ALTER is
  --    guarded for the same reason the role creation is: on a re-run the schema is already
  --    svc_migration's, and the actor would no longer own it.

  -- restores ownership to pg_database_owner, and a gate written from a constant cannot
