## Tenancy and topology

**C1 — Tenant root: `workspaces.id` (ruled).** FC-1 flips the earlier chat-rooted default: the pre-ruling adjudication kept `chat_settings.id` as the physical key because a rename bought zero isolation while costing a dual-key window; the product owner then ruled that multi-workspace/multi-account/multi-surface is the product. That is the exact contingency the default reserved ("if web-first onboarding / multi-chat / chatless tenants are on the roadmap, the workspace root should win now"). #722's neutral-`tenant_id`-at-service-boundaries rule is what makes the flip affordable: service code re-keys once, to the neutral name; only resolution changes. #721's workspaces *direction* is thereby resurrected; its letter is not (24 recorded quality flags — the five load-bearing ones are cited in this plan as FLAG-1/2/3/7/10; the full inventory is fleet-side working-set material, available on request, and nothing here depends on the other nineteen).

**C2 — Topology: multi-service (envelope-ruled scale-out; role separation justified on its own grounds).** FC-0 (thousands of tenants) overrules #721's single-process non-goal (N3) for **horizontal replicas** — that much is the product owner's envelope. The three-**role** split is justified separately (pass-2 correction, review A §4.3: tenant cardinality alone does not mandate role separation): (1) R5/H2 fault isolation — a poisoned publish pipeline must not take down ingress ack latency; (2) webhook ingress needs an always-up HTTP surface deploy-decoupled from workers; (3) the deployment already runs API and worker as two Railway services today — the target topology is the status quo plus an elected clock, not new machinery.

**C4 — RLS: enforce early, constant-expression policies.** RF-R3 as ratified (see map above); #721's RLS-later posture (N7) overruled; #721's composite tenant FKs (D12) kept — they complement RLS, catching what policies structurally cannot (cross-workspace FK references). Extended to credentials by the typed XOR owner FKs in `02` §2 (a polymorphic owner id would have broken the convention exactly where tokens live).

## Pipeline and execution

**D1 — Two proposed pipelines become one, layered.** #721's domain decomposition (intents/approvals/attempts/outcomes) and #722's jobs/leases both survive — at different layers: the **intent ledger is product state**, **jobs are execution units**, `provider_operations` is the external-effect rail. Three independent derivations converged on intent-centric domain state (#721, cold design, the shipped delivery-state trajectory), which also closes RF-G1. Only a lease holder touches a provider.

**D2 — Outbox never authorizes effects.** #722's semantics win; #721's outbox-executes model loses (it reopens the duplicate-effect window and had no lease concept — FLAG-7). The outbox is a delivery record + wake-up hint — and for sends it is the *single* authority on delivery state (`02` §6), so no second machine tracks "did it send".

**C9 — Cancellation is cooperative.** #722's model: `cancel_requested` flag, honored at checkpoints; `publishing → cancelled` forbidden; reconciler consults the flag where a real choice remains.

**C5 — Scheduling: O(due) clock + dispatcher as a named build item.** Precomputed `next_*_at` columns, one indexed scan per tick, all work in jobs (H3). #721's in-process scheduler (N10) overruled. The dispatcher is built inside `04` L.7 — #722 described it in prose but never gave it an increment.

**G1 — Real-account serialization and Meta budgets key on `provider_account_ref`.** One in-flight publish per real Instagram account by constraint (`02` §3-keys key 4), and Meta-side budget handling addresses the real account — both survive workspace-owned account rows precisely because they key on the Meta id, not our PK.

**G5 — `review_required` in both vocabularies.** Adopted from #722 into the intent ledger too; #721's enums lacked failure terminals entirely (FLAG-3). Poison edges added to jobs (#722 intra-fix).

**C8 — Idempotency keys compose.** Slot key + live-subject key including `ig_account_id` (FLAG-2 fix) + publishing-exclusivity key — stated fully in `02` §3-keys. The slot key carries no intent-kind discriminator: exactly one kind exists, and the closed-enum convention makes a future kind a deliberate migration that widens the key, so pre-adding it bought nothing.

**C10 — History uniqueness: interim then target.** Interim (pre-ledger): validated unique on `posting_history.queue_item_id` after the human-gated remediation of the 6 known production duplicate groups (TT:P0-03 prep, `04` 0.3). Target: one terminal outcome per intent (`02` §3-keys key 3). The interim step is not skippable — the backfill inherits its cleanliness.

## Pass-4 decisions (2026-08-03 — the #732 liveness finding and the sign-in/invitation rulings, applied)

Same relitigation rule. "#732" cites the token-liveness analysis (comment 5165860199 on #732); "auth comment" / "invitation comment" cite comments 5168818430 / 5170243666 on PR #731. The product-owner rulings this pass applies are recorded as FC-5/FC-6 in `00`.

**D31 — Publish-time credential liveness: a definitive provider auth-rejection demotes, from any call; no standing pre-publish probe; no fourth credential state.** The #732 finding: both `02` governing transition lists were stated-complete with the **refresh path as the only entry trigger** into the demote/notify/stop/recover machinery, and the refresh cadence — the one number bounding dead-token detection latency — had no `05` row. A publish-time 190 on a calendar-valid credential therefore demoted nothing: the account stayed `active`, the dispatcher kept minting intents, and the reauth campaign never fired — the 2026-05 incident reproduced *inside* the new system, at bounded cadence instead of retry-forever. The fix is four pieces, no new state, no new job kind, no new grants: (1) the `02` §2 liveness edge — a definitive auth-rejection (190 without revocation subcode; unparseable-token class per the corrupt-phrase discrimination already proven on `main`) from ANY Meta call flips `oauth_credentials → expired` + `ig_accounts → reauth_required` in the observing worker's same transaction; (2) the `05` refresh-cadence row, decoupled from expiry proximity, with the Meta refresh-eligibility 0.4 item; (3) the L.6 dead-token symptom gate; (4) this record. Two explicit rejections ride with it. **A standing pre-publish liveness probe is rejected:** with first-rejection-demotes, a dead token costs exactly one wasted attempt before dispatch stops — a per-publish probe buys back that single attempt at +1 Meta call on every healthy publish forever, the same trade `02` §8 already refused for quota (and which legacy `main` refused too: the #705/#707 pre-publish quota gate is fail-open by design). If the S.5 canary ever arms the §8 pre-check, auth-classification on that same call comes free. **A fourth credential state ("present-but-rejected") is rejected:** `expired` already carries the provider-verdict semantic — "the provider determined the token is gone" is its definition, and the `07` §3 decrypt-failure maps to it; present-but-rejected ≡ credential `expired` + account `reauth_required`. What product additionally needs is *message* differentiation (corrupt vs session-expired) — an error-class detail in `last_error`, with `main`'s classifier discrimination carried forward, not a state.

**D32 — Sign-in is Google OIDC; identity keys on the provider subject, never email (FC-5 applied).** Removes: `otp_challenges` and the whole challenge machinery (`07` §1), the `send_email` OTP producer, the `otp_email`/`otp_ip` rate scopes, the `email_change` purpose (email is a provider claim now), one auth-plane sweep enumeration, and the `email_otp` provider value. Adds: the `oauth_states` widening (`07` §2 — purposes `signin`/`link`, purpose-conditional context nullability, cookie-nonce CSRF for the anonymous case), the OIDC verification utility (JWKS, small), and two egress-allowlist hosts at X.3. Sessions survive verbatim — the ruling replaced the *proof*, not the session. **The identity rule:** `user_identities.external_id` = the OIDC `sub` claim; the verified email is metadata refreshed at sign-in; `users.primary_email` fills when NULL and conflicts surface rather than merge — emails are mutable and recyclable, so email-keyed identity is an account-takeover primitive. **Grounding (FC-5.4):** the existing web-application Google OAuth client (Drive redirect flow) makes reuse a second client ID + non-sensitive scopes under the reviewed consent screen — no new app, no consent-screen review; the consent screen's publishing status is the one conditional (owner item below). **Migration burden: zero** — `email_otp` rows could only have existed after X.3 shipped; the ruling landed before any row it invalidates could exist, which is itself the argument for folding it in pre-ratification.

**D33 — Invitations under FC-6: the token is the accept credential; identity constraints are per-provider from day one.** The ruled shape (the panel's data model wearing B's delivery): `token_hash` UNIQUE is THE accept credential; `email` is nullable, channel-conditionally required; the Telegram-side columns are `invited_tg_user_id` (constraint input) and `invited_channel_hint` (display only) — the pass-5 split of the original advisory-hint column; `accepted_email_matched` records proof-ran-and-matched (`true`) vs constraint-bypassed-for-lack-of-comparable-proof (`false` — a recorded skip; mismatch never lands); accept is one CAS + the member INSERT in the same transaction, with `workspace_members`' PK as the double-membership guard; `uq_invite_live` stays (NULLs exempt; re-invite = insert-new + revoke-prior in one transaction, which the partial unique then enforces). **The per-provider acceptance constraint, and why it is per-provider on day one rather than an Apple accommodation:** provider identity namespaces differ *now* — Telegram supplies no email address today, so an email-keyed accept was already impossible for one of our two launch providers; Apple's relay (a verified address that will never equal a typed one) is a **second instance of an existing rule**, not a future exception needing an escape hatch. The constraint table (**as amended pass 5 — R4's username finding: no mutable identifier is ever proof**): **Google** — the verified id_token email must equal the row's email when set (mismatch refuses; `true`); **Telegram** — the tapping identity's **immutable numeric user id** must equal `invited_tg_user_id` when set (mismatch refuses; `true`); a username is delivery/display data (`invited_channel_hint`) and **never participates in the match** — usernames are mutable and recyclable, exactly the property D32 already names as an account-takeover primitive, applied here one level finer; no comparable value ⇒ token possession accepts, skip recorded as `false`; **Apple (descoped)** — relay ⇒ recorded skip, a path that already exists because Telegram exercises it from the first commit. An implementer reading "B" without this decision would make email the key, because that is B's obvious reading — this entry exists to prevent exactly that. Zero new states, zero new commands, one computed INSERT value and one notification write; the D33 audit boolean graduates to an authorization input, written and read in the same transaction (no TOCTOU). If the notification is ignored, the acceptor stays a member — the safe terminal state, not a dangling obligation. **Rejected shapes:** uniform two-phase for all admin invites (adds friction exactly where the identity proof already binds the acceptor to the invited identity — a matched proof is stronger evidence than an inviter's glance at a name); shorter admin-invite expiry (narrows the window, closes nothing — a screenshot inside the window still silently mints an admin); status quo admin-on-token-possession (the silent-admin hole the ruling's property forbids).
