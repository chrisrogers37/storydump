## Summary

A new command-line tool, `storydump`, built on the target tier only: a pure HTTP client of the
target API (and of Railway's API for deploy status), with **one pathway** for everything it does.
It exists because the tool the last two days needed did not: validating the float, the first
burst, a duplicated card and two deploys took about 55 one-off SQL files run through the Railway
seam, none reusable, none tested. The first release is **diagnostics first** — the read views those
files answered, with `--json` and `--watch` — plus the command port's existing verbs as writes,
`health`, `deploys`, `webhook` and `doctor`. Writes are attributable: a token is either bound to a
person (audited as that person, with the token's name as the client label) or is a workspace
service identity (audited under its own name). The legacy `cli/` package (31 commands over legacy
services and a direct database connection) is deleted in the same workstream; it may be
referenced for scope, never imported. `psql` through the Railway seam remains the runbook's
emergency escape hatch and is not part of the CLI.

## Context

- **Nothing deployed runs the legacy tier** (worker on the target composition root since
  2026-08-24, the API since 2026-08-31), and the target tier imports nothing from
  `src/services/core`. The legacy CLI is the last legacy consumer; the owner does not use it — it
  was for local agent execution and testing. #1216 already holds the retirement plan; its step 4
  is "move the CLI onto the target API (`service_tokens` + CLI-over-API)", the plan's X.2 item.
- **The schema anticipates this.** `service_tokens` (migration 060) has a name, a hash-only
  secret, a role from the closed set `operator` / `readonly`, expiry, revocation and last-use
  stamps. The audit trail's channel constraint already allows `cli`. What is missing: a subject
  binding for person-bound tokens, the minting route, the bearer check, the read views, the CLI.
- **The plan's posture rules apply** (`02` §7, F.4): the API runs as a login role under row-level
  security; every cross-tenant capability is a named, reviewable object. This spec adds none: its
  reads are tenant-scoped, looped over the principal's workspaces.
- **Owner rulings during discovery (2026-09-15):** API-only, one pathway; diagnostics first plus
  the existing commands; both principal kinds in one token model; `--json` with stable exit codes,
  `--watch` on the read views, a `doctor` verb; a new in-repo package with the legacy `cli/`
  deleted now; the web stays the settings surface, Telegram a card-and-tap channel; other channels
  (WhatsApp, SMS) are their own kindle later — the CLI's verbs must not assume Telegram.

## Design

### 1. Shape and boundaries

- **Package:** `storydump_cli/` in this repository, console script `storydump`. It imports from
  `src/` exactly one module: a dependency-free vocabulary module (the command kinds, the refusal
  reasons, the intent states, the JSON shapes) that the server imports too. A test pins that
  `storydump_cli` imports nothing else from `src` and never opens a database connection.
- **Transports:** the target API (bearer token) for every read and write against our system;
  Railway's API (the developer's own Railway credential) for deploy status. Nothing else.
- **Deleted with it:** the legacy `cli/` package, its Makefile targets, and its four entries in the
  never-run lists of `CLAUDE.md` / `AGENTS.md` (the doc test that pins those lists changes with
  them). The never-run list keeps only what is genuinely destructive.
- **Not replaced:** `psql` through `railway run` stays the runbook's escape hatch for questions the
  views do not answer. The CLI covers the recurring questions; it does not try to be `psql`.

### 2. Identity: one token model, two principal kinds

- `service_tokens` gains a nullable `user_id` (its `workspace_id` is already nullable, 060). A
  token with a user is **person-bound**: it carries no workspace, acts as that person in every
  workspace the person is a member of, inherits and can never exceed the person's membership role
  there, and is audited as the person with the token's `name` as the client label (so the trail
  reads "Chris, via claude-code on chris-mbp"). A token without a user is a **workspace service
  identity**: it carries its workspace and, in the first release, **reads only** — the command
  port authorizes writes by workspace membership and a service identity has none (plan fork F10);
  a write-capable service principal is a later slice.
- **Minting:** only from a signed-in session, on the web's Settings › API tokens panel (the first
  step of the first-time clock) — a person mints their own person-bound token at `POST /me/tokens`;
  an admin or owner mints a service identity at `POST /workspaces/{ws}/tokens` (list and revoke
  beside each). The secret is shown exactly once and stored only as its SHA-256, the pattern
  sessions already use. Never minted by a migration, by a script holding the database URL, or by
  another token; the CLI lists and revokes, it does not mint.
- **Bearer check:** the API resolves `Authorization: Bearer <token>` to a principal (hash lookup,
  not expired, not revoked; `last_used_at` stamped), then sets the tenant and actor GUCs exactly
  as a session does: `app.tenant_id` = the workspace the request names, `app.actor_kind` = `user`
  for a person-bound token or `operator` for a service identity (both already in the audit
  trail's actor constraint), `app.actor_user_id` when bound, `app.channel` = `cli`. Tokens are
  admitted to an explicit route allowlist (the views, the command route, the principal's own
  profile and tokens); every other route stays session-only. One `cli_command` audit row per
  command carries the token's id and name and the command's idempotency reference.
- **Workspace selection:** the CLI's `--workspace` flag names one; a read without it runs over
  every workspace the principal may read; a write requires one.
- **Roles:** `readonly` may call the read views only; `operator` may also call the command route.
  A person-bound token's effective role is the lesser of the token's role and the person's
  membership role.
- **CLI side:** `storydump login` reads the secret from a prompt or stdin and stores it in the OS
  keychain by default, failing closed where none exists (`--insecure-storage` for a 0600 file;
  `STORYDUMP_TOKEN` overrides for agents and CI — plan decision F2); `whoami` shows the principal,
  the role and the workspaces; `tokens list | revoke` act on the principal's own tokens.

### 3. The read views

Each is one API endpoint under `/ops/…`, one tenant-scoped query run under the token's workspace
(the principal's membership decides which workspaces it may read; the CLI loops them). No new
cross-tenant privilege: a true fleet-wide surface for a platform operator is out of scope (named
below). Every view is bounded (a `LIMIT`, a time window) and returns rows with their workspace id.

| Verb | What it answers | Reads |
|---|---|---|
| `story <id>` | the timeline: minted, served, tapped, every state, permits (variant, outcome, error), waits (class, rung), cards | `post_intents`, `audit_events`, `provider_operations`, `channel_outbox` |
| `cards <story>` | every card and its edits, by binding and channel, including adopted twins | `channel_outbox`, `channel_bindings` |
| `floating` | approved stories carrying a debit: step, counters, class, rung, next run | `post_intents`, `jobs`, `audit_events` |
| `account <handle\|id>` | cap per day, today's count, next slot, the last outcomes | `ig_accounts`, `daily_post_counts`, `post_intents` |
| `jobs` | due, leased, failed; by kind and lane; oldest age | `jobs` |
| `outbox` | pending, ambiguous, failed rows by binding; the paced holds | `channel_outbox`, `rate_counters` |
| `burst [--since]` | the post-burst read: taps and outcomes, refusals and fresh-url acceptances, siblings past a waiter, review cards | the four ledger tables |
| `posture` | the migration ledger, the connected role and its `BYPASSRLS`, RLS state per table, the doors census | catalogs and the migration ledger (a read grant for the API's role where needed) |

### 4. The writes

`approve`, `skip`, `reject`, `posted`, `cancel`, `resolve <story> <retry|posted|giveup>`,
`pause`, `resume`, `sync` call `POST /workspaces/{ws}/commands/{command}` with the bearer token —
the same command port a tap or a web click uses, so admission, tenancy and audit apply unchanged.
The CLI prints the same answer a tap would get. No verb writes to the database by any other path.

### 5. Environment verbs

- `health`: the API's `/health` plus the worker's heartbeat freshness as the API reports it.
- `deploys [--watch]`: the latest deployment per service from Railway's API, with its commit.
- `webhook status | register`: the existing `scripts/telegram_webhook.py` behaviour, absorbed, with
  its rule that no secret ever reaches the terminal.
- `doctor`: checks the token (present, valid, role), the API (reachable, version), the Railway link,
  the local configuration and the migration ledger against the repository, and reports each as
  ok, wrong or missing with a one-line fix.

### 6. Contracts

- `--json` on every verb emits one envelope, `{"v": 1, "kind": "<verb>", "data": …, "error": null}`,
  and on failure `{"v": 1, "kind": "<verb>", "data": null, "error": {"code", "reason", "detail",
  "fix"}}`; a read's `data` is always `{"workspaces": [{"workspace_id", "rows"}]}`; `--watch --json`
  emits one envelope per read. Shapes are versioned and changes are additive. Human output is
  aligned tables.
- Exit codes: `0` ok · `1` not found · `2` refused by the command port (the reason word in the
  output) · `3` not authorized (bad, expired or revoked token; wrong role; not a member) · `4` API
  unreachable or failed · `5` Railway unreachable · `6` a watched condition ended in failure ·
  `64` bad usage. The CLI owns its exit codes (Click's own are not exposed).
- `--watch` re-reads a view on an interval (default 30 s) and prints only rows that changed, keyed
  by id; it exits on a terminal condition where one exists (a burst drained, a deploy finished).
- **Redaction at the client:** a token is printed once, at mint, and never echoed; anything
  matching a token, a database URL or a webhook secret is redacted before printing.
- **Refusals are answers, not failures:** a command the port refuses prints the CLI's own sentence
  for the reason, naming the fixing verb, and exits `2`; a re-run of a command already done replays
  and exits `0` (the idempotency key is deterministic, the web's convention); only transport and
  authorization failures are errors. The Telegram adapter's wording never appears in a terminal.
- **Channel-neutral:** a card is a card on a binding of whatever channel; verbs and shapes carry the
  channel as data and assume nothing about Telegram.

### 7. Testing

Three layers, all on the existing harness, every behaviour written red first with a named mutation:

1. **View gates** against the replayed schema, driving the API in-process as the ingress login
   role: rows, bounds, and that a principal sees only its workspaces.
2. **Auth gates:** a revoked or expired token is refused; a person-bound token cannot exceed the
   person's role; a `readonly` token cannot write; the minting route refuses a non-admin; a minted
   secret is stored only as its hash; the audit row of a CLI write carries `channel = 'cli'` and
   the principal.
3. **CLI tests** driving every verb against the in-process API: the JSON envelope, the exit codes,
   `--watch`'s change-only output, the redaction, `doctor`'s findings. The import-boundary test pins
   that the package reaches `src` only through the vocabulary module.

### 8. Delivery

Three PRs in order, each with the repository's process (tests first, two review lenses, a
mutation battery, CI, admin squash):

1. **Tokens:** the vocabulary module (sets, envelope, exit codes, sentences); the `user_id` column
   and the subject check (one migration with its `07` block and manifest row); the runner's grant
   on its own ledger; bearer authentication with the route allowlist; the minting, list and revoke
   routes; the web's tokens panel; `login`, `whoami`, `tokens list|revoke`.
2. **Reads:** the eight `/ops` views and their verbs, with `--json` and `--watch`.
3. **Writes and the rest:** the command verbs, `health`, `deploys`, `webhook`, `doctor`; the
   deletion of the legacy `cli/`, its Makefile targets and never-run entries, with the docs.

## Decisions

| Decision | Choice | Why |
|---|---|---|
| Pathway | API-only, one pathway; Railway's API for deploys | one enforcement point for auth, tenancy, admission and audit; how `kubectl`, `gh` and the Stripe CLI are built |
| Diagnostics without cross-tenant privilege | tenant-scoped views looped over the principal's workspaces | no new capability class; F.4-compatible; sufficient at the current scale |
| Identity | one token model, two principal kinds (person-bound reads and writes; service identities read-only in v1, F10) | every write attributable to a person; automation reads under its own name; the command port's membership rule stands |
| Token storage | keychain by default, fail closed, 0600 file by opt-in, the variable for agents (F2) | the `gh` pattern; secure by default with an explicit escape hatch |
| Minting | a signed-in admin only; hash-only; shown once | the sessions pattern; no secret in a migration or a script |
| First slice | diagnostics first plus the existing commands | the tool the last two days lacked; the web app already owns settings, media and users |
| Packaging | new in-repo package; legacy `cli/` deleted now | shared tests against the replayed schema; the last legacy consumer goes first |
| Escape hatch | `psql` via the Railway seam stays in the runbook | the CLI covers recurring questions; forensics keep raw SQL |

## Out of scope

- A platform-operator role and fleet-wide views across tenants the principal is not a member of
  (a later slice, with SECURITY DEFINER doors in the `02` §7 inventory when it comes).
- Other channels (WhatsApp, SMS): their own kindle; the CLI is built channel-neutral for it.
- The rest of the legacy tear-out (#1216 steps 1–3 and 5): its own plan.
- Media indexing, category-mix editing, user management, Drive connect: the web app's; not verbs.
- Shell completion and rich TUI: after the first release.
- Rebuilding the Telegram settings slash commands or the Mini App: deleted with the legacy tier,
  not restored.
